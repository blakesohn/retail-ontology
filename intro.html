Why Ontology on Snowflake?

기존 데이터 플랫폼의 한계와 온톨로지 기반 접근의 필요성

Based on: Ontology on Snowflake Blog Series by Tianxia Jia, Snowflake Builders Blog — Part 1 · Part 2 · Part 3

1. 기존 데이터 플랫폼의 한계

현대 기업은 테이블과 JOIN으로 사고하지 않습니다. 사람, 조직, 자산, 이벤트, 프로세스로 사고합니다.
하지만 기존 데이터 플랫폼은 이러한 비즈니스 개념을 직접 모델링할 수 없습니다.

구체적 시나리오: Supply Chain 담당자의 질문

Supply Chain 담당자가 실제로 묻는 질문과, 이를 기존 방식으로 답변하려 할 때의 문제를 살펴봅니다.

비즈니스 질문왜 어려운가
"Lithium Carbonate 공급이 중단되면 어떤 최종 제품이 영향받아?" 원자재 → 서브어셈블리 → 제품까지 BOM 트리를 재귀적으로 탐색해야 합니다. 단일 JOIN으로 불가능하고, 깊이가 몇 단계인지 미리 알 수 없습니다.
"우리 회사의 모든 자산(부품+제품)은 총 몇 개야?" COMPONENTS 테이블과 PRODUCTS 테이블은 서로 다른 스키마입니다. "자산"이라는 상위 개념이 DB에 존재하지 않으므로, 개발자가 수동 UNION을 작성해야 합니다. 새 자산 유형 추가 시 쿼리 수정이 필요합니다.
"Battery Cell 4680의 대체 부품이 있으면, 그 대체 부품의 공급업체는?" 부품 대체 관계 → 대체 부품 식별 → 공급 계약 → 공급업체까지 3개 테이블을 순차 탐색해야 합니다. 관계의 방향성과 연결 경로를 개발자가 직접 파악해야 합니다.
"이번 달 모든 비즈니스 활동(주문+배송+계약) 건수는?" ORDERS, SHIPMENTS, SUPPLY_CONTRACTS는 전혀 다른 테이블입니다. "비즈니스 활동"이라는 추상 카테고리로 묶는 개념이 DB에 없습니다.

Semantic View만으로는 왜 부족한가?

Semantic View는 "컬럼이 무슨 의미인지"를 정의하는 데 탁월합니다. 하지만 "엔티티 간 관계가 어떤 구조인지"는 정의할 수 없습니다.
필요한 능력Semantic ViewOntology
컬럼 의미 정의
"REGION은 지역, PRICE는 가격"		 가능 가능
테이블 간 JOIN 경로 정의
"ORDERS.PRODUCT_ID = PRODUCTS.PRODUCT_ID"		 가능 가능
클래스 계층 구조
"Component와 Product는 모두 PhysicalAsset이다"		 불가능 가능
재귀 관계 탐색
"BOM 트리를 끝까지 탐색: A→B→C→...→N"		 불가능 가능 (Graph UDF)
관계의 속성 정의
"assembles_from은 transitive, substitutes_for는 symmetric"		 불가능 가능 (Metadata)
추론/도출
"A가 B를 공급하면, B는 A로부터 공급받는다 (역방향 자동 생성)"		 불가능 가능 (Inference)
Zero-code 확장
"새 엔티티 추가 시 기존 쿼리 변경 없이 자동 포함"		 불가능 (ALTER 필요) 가능 (SP 호출)
정리

Semantic View는 "테이블 안의 데이터가 무슨 뜻인지"를 AI에게 알려줍니다. 이것만으로도 Text-to-SQL의 정확도가 크게 올라갑니다.

Ontology는 여기에 "테이블 간의 관계가 어떤 구조이고, 비즈니스 개념이 어떻게 분류되며, 어떤 추론이 가능한지"를 추가합니다. 관계가 복잡하고, 계층이 깊고, 추론이 필요한 도메인에서 Semantic View 위에 Ontology를 얹는 것이 핵심입니다.

왜 기존 방식으로는 어려운가?

의미(Meaning)의 파편화

데이터는 웨어하우스에, 시맨틱은 카탈로그나 애플리케이션 코드에, AI는 공유된 개념 모델 없이 동작합니다.

취약한 SQL & 중복 로직

비즈니스 의미가 스키마, ETL 코드, 애플리케이션에 분산되어 있어 로직이 중복되고 변경에 취약합니다.

느린 변경 대응

비즈니스가 변경되면 쿼리와 파이프라인을 다시 작성해야 합니다. 스키마 변경 → 전체 시스템 영향.

AI의 맥락 부재

AI 시스템이 비즈니스 컨텍스트 없이 동작합니다. "조직"이 뭔지, "자산"이 어떤 테이블에 있는지 모릅니다.

핵심 문제

AI 기반 추론, 분석, 자동화를 지원하려면 플랫폼이 단순히 사실(Fact)을 저장하는 것을 넘어서, 비즈니스가 어떻게 작동하는지를 모델링해야 합니다.

2. 온톨로지란 무엇인가?

온톨로지는 도메인의 형식적 표현(Formal Representation)으로, 다음을 정의합니다:

객체 (Objects)

추상적 개념과 구체적 인스턴스 모두 포함. 예: "물리적 자산" (추상) → "부품", "제품" (구체)

관계 (Relationships)

객체 간 연결 방식. 예: Supplier supplies Component, Product assembles_from Component

계층 구조 (Hierarchies)

상속과 분류 체계. 예: Component is-a PhysicalAsset is-a Entity

속성 & 제약 (Properties & Constraints)

속성, 행동, 규칙. 예: assembles_from은 transitive — A→B→C이면 A→C도 성립

기존 스키마와의 핵심 차이: 온톨로지는 사실(Facts)과 의미(Meaning)를 분리합니다.
사실은 구체적이고 안정적입니다. 의미는 선언적으로 정의되며 독립적으로 진화합니다.

3. 핵심 아키텍처 원칙

Ontology on Snowflake의 설계 원칙

사실(Facts)은 한 번만 저장하고, 의미(Meaning)는 메타데이터로 정의하며, 추상화(Abstraction)는 동적으로 생성합니다.

이 분리를 통해 물리적 데이터 모델은 안정적으로 유지되면서, 비즈니스 시맨틱은 독립적으로 진화할 수 있습니다 — 스키마 변경, 중복 로직, 취약한 쿼리 패턴을 제거합니다.

기존 방식
  • 비즈니스 의미가 스키마, ETL, 앱 코드에 분산
  • 비즈니스 변경 → 쿼리/파이프라인 재작성
  • 새 엔티티 추가 → 테이블 DDL, 뷰, JOIN 모두 수정
  • AI는 비즈니스 맥락 없이 동작
Ontology on Snowflake
  • 비즈니스 의미가 메타데이터 테이블에 집중
  • 비즈니스 변경 → 메타데이터 INSERT만
  • 새 엔티티 추가 → SP 호출로 뷰 자동 재생성
  • AI가 온톨로지를 통해 비즈니스 맥락을 이해

4. 5-Layer Architecture

Ontology on Snowflake는 세 가지 데이터 레이어와 두 가지 인텔리전스 레이어로 구성됩니다.

Layer 5: Cortex Agent
자연어 질문 → 의도 파악 → 적절한 Semantic Model로 라우팅
↓
Layer 4: Semantic Views (3-Model Strategy)
Concrete Model + Ontology Model + KG/Metadata Model
↓
Layer 3: Abstract Views
메타데이터에서 자동 생성되는 추상 개념 뷰 (VW_ONT_*)
↓
Layer 2: Ontology Metadata
클래스, 관계, 계층 구조, 추론 규칙 — 의미를 선언적으로 정의
↓
Layer 1: Physical Storage
KG_NODE + KG_EDGE — 사실(Facts)만 저장하는 범용 그래프 구조

각 레이어의 역할

Layer역할핵심 원칙변경 시 영향
L1사실(Facts) 저장모든 엔티티 = 객체, 모든 연결 = 관계데이터 추가/변경만 — 구조 불변
L2의미(Meaning) 정의비즈니스 의미를 메타데이터 테이블로 선언INSERT로 확장 — 코드 변경 없음
L3추상화(Abstraction) 생성메타데이터에서 자동 컴파일된 뷰SP 호출로 자동 재생성
L4쿼리 인터페이스목적별 3개 Semantic ModelAgent가 의도에 따라 자동 선택
L5자연어 인터페이스질문 의도 → Tool 라우팅새 Tool 추가 시 Agent 확장

시나리오: "물류 업체(LogisticsProvider)" 를 새로 추가하면?

Supply Chain에 새로운 엔티티 유형인 물류 업체가 추가되는 상황을 각 레이어별로 추적합니다.

L1 Physical Storage — 데이터 입력

물류 업체 데이터를 KG_NODE에 INSERT합니다. 테이블 구조 변경은 없습니다.

INSERT INTO KG_NODE VALUES ('LP_1', 'LogisticsProvider', 'Maersk', OBJECT_CONSTRUCT('FLEET_SIZE', 350, 'REGION', 'Global'));
L2 Ontology Metadata — 의미 등록

"LogisticsProvider는 Organization의 하위 클래스다"라는 의미를 메타데이터에 등록합니다.

-- 클래스 등록: "물류 업체는 조직의 하위 유형" INSERT INTO ONT_CLASS VALUES ('LogisticsProvider', 'Organization', FALSE, '물류 업체'); -- 소스 매핑 등록: "KG_NODE에서 NODE_TYPE='LogisticsProvider'인 행" INSERT INTO ONT_CLASS_MAP VALUES ('LogisticsProvider', 'KG_NODE', 'NODE_TYPE', 'LogisticsProvider');
L3 Abstract Views — 자동 재생성

SP를 한 번 호출하면, L2 메타데이터를 읽어 뷰가 자동으로 재생성됩니다.

CALL SP_GENERATE_ONTOLOGY_VIEWS(); -- 결과: -- ✓ VW_ONT_LOGISTICSPROVIDER 뷰 새로 생성됨 -- ✓ VW_ONT_ORGANIZATION 뷰 갱신됨 (Supplier + LogisticsProvider) -- ✓ VW_ONT_ALL_ENTITIES 뷰 갱신됨

핵심: 이제 SELECT * FROM VW_ONT_ORGANIZATION을 실행하면 기존 Supplier와 새로 추가된 LogisticsProvider가 자동으로 함께 조회됩니다. 기존 쿼리는 한 줄도 수정하지 않았습니다.

L4 Semantic Views — 자동 반영

Ontology Semantic View (Model 2)는 VW_ONT_ORGANIZATION 뷰를 소스로 사용하므로, L3의 뷰가 갱신되면 Semantic View도 자동으로 새 데이터를 포함합니다.

변경 작업: 없음. Semantic View는 뷰를 참조하므로, 뷰가 바뀌면 자동 반영됩니다.
다만 새 엔티티의 고유 속성(FLEET_SIZE 등)에 대한 Dimension/Metric을 추가하려면 ALTER SEMANTIC VIEW가 필요합니다.
L5 Cortex Agent — 즉시 답변 가능

사용자가 "우리 조직은 총 몇 곳이야?"라고 물으면, Agent는 ontology_query → VW_ONT_ORGANIZATION을 통해 Supplier + LogisticsProvider를 합산하여 답변합니다.

변경 작업: 없음. Agent 재배포 불필요. 기존 질문이 자동으로 새 데이터를 포함합니다.
요약: 새 엔티티 유형 추가에 필요한 작업은 L1에 데이터 INSERT + L2에 메타데이터 INSERT 2줄 + SP 호출 1번뿐입니다. L3~L5는 자동으로 반영됩니다. DDL 변경, 뷰 수작업, Agent 재배포 없이 시스템이 확장됩니다.

5. 왜 3개의 Semantic Model인가?

하나의 Semantic Model로 모든 질문 유형을 처리할 수 없습니다.
구체적 분석, 추상적 추론, 구조 탐색은 각각 다른 트레이드오프를 요구합니다.
Model대상 질문소비 레이어예시
Model 1: Concrete
KG / 원본 테이블		 구체적 데이터 조회
(가격, 수량, 날짜, 필터)		 L1 Concrete Views "지역별 공급업체 수는?"
"전자제품 평균 가격은?"
Model 2: Ontology
Abstract Views		 추상적 cross-type 추론
(계층 통합, 다형적 질의)		 L3 Abstract Views "모든 자산 수는?"
"비즈니스 활동 유형별 건수는?"
Model 3: Metadata
ONT_* 테이블		 구조/거버넌스 탐색
(클래스, 관계, 규칙 조회)		 L2 Metadata "어떤 클래스가 존재해?"
"transitive 관계는?"

각 Model은 서로 다른 질문 유형에 최적화되어 있으며, 일관성은 모든 Model이 동일한 온톨로지 메타데이터에서 파생되기 때문에 보장됩니다.

6. 온톨로지의 핵심 가치

가치 1: Zero-Code 확장성

기존: 새 엔티티 추가

CREATE TABLE → INSERT 쿼리 작성 → VIEW 생성 → 기존 UNION 뷰 수정 → Semantic Model 수정 → 최소 5개 SQL 수작업

온톨로지: 새 엔티티 추가

ONT_CLASS에 INSERT 1줄 → ONT_CLASS_MAP에 INSERT 1줄 → SP_GENERATE_ONTOLOGY_VIEWS() 호출 → 뷰 자동 재생성, 기존 쿼리 변경 없음

가치 2: 안정적인 쿼리

기존: "모든 사람" 조회

SELECT * FROM PLAYERS UNION ALL SELECT * FROM COACHES
새 역할(Referee) 추가 시 → 쿼리 수정 필요

온톨로지: "모든 사람" 조회

SELECT * FROM VW_ONT_PERSON
Referee 추가 시 → 쿼리 변경 없이 자동 포함

가치 3: AI에 비즈니스 맥락 제공

기존 AI: Text-to-SQL

"모든 자산 수"를 물으면 AI가 어떤 테이블을 JOIN해야 하는지 추측해야 합니다. Component와 Product가 "자산"이라는 맥락이 없습니다.

온톨로지 + AI

온톨로지가 "PhysicalAsset = Component + Product"를 알려줍니다. AI는 VW_ONT_PHYSICAL_ASSET을 정확하게 선택하여 답변합니다.

가치 4: Multi-Tool 연쇄 추론

단일 SQL로는 불가능한 질문

"Lithium Carbonate가 사용되는 최종 제품은 뭐고, 그 제품들의 총 주문 건수는?"

이 질문은 (1) Graph Traversal로 원자재 → 최종 제품 추적 후, (2) Concrete Model로 해당 제품의 주문 건수를 집계해야 합니다. Agent가 두 개의 Tool을 연쇄 호출하여 답변합니다.

7. 어떤 경우에 적합한가?

적합한 경우부적합한 경우
엔티티 간 복잡한 관계가 핵심인 도메인단순 집계/리포팅만 필요한 경우
계층 구조 (BOM, 조직도, 카테고리 트리)가 있는 도메인플랫한 트랜잭션 테이블만 있는 경우
비즈니스 모델이 자주 변경되는 환경스키마가 고정되어 변경이 거의 없는 환경
Cross-type 질문이 빈번한 경우 ("모든 자산", "전체 활동")항상 특정 테이블만 조회하는 경우
AI/Agent 기반 자연어 인터페이스를 구축하려는 경우SQL 대시보드만으로 충분한 경우

적합 도메인 예시

Supply Chain

공급업체 → 부품 → 제품 → 주문 → 배송의 복잡한 관계망

Healthcare

환자 → 진단 → 치료 → 약물 → 의료진 간 관계

Financial Services

고객 → 계좌 → 거래 → 상품 → 규제 간 관계

Telecom / IT

네트워크 장비 → 서비스 → 고객 → 장애의 의존 관계
