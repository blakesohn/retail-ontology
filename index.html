Layer 1은 왜 필요한가?

10개의 서로 다른 테이블(SUPPLIERS, COMPONENTS, PRODUCTS 등)에 분산된 데이터를 하나의 통합 그래프 구조(KG_NODE + KG_EDGE)로 변환합니다. 이렇게 하면 "공급업체에서 원자재까지 몇 단계를 거치는가?"처럼 테이블을 넘나드는 관계 탐색을 단일 테이블의 재귀 쿼리로 처리할 수 있습니다.

Before — 원본 테이블
10개 테이블에 각각 다른 PK/FK 구조. 공급업체→부품→제품 관계를 추적하려면 SUPPLY_CONTRACTS, BOM, PRODUCTS를 수동 JOIN해야 함. 새로운 관계 추가 시 스키마 변경 필요.
After — KG_NODE + KG_EDGE
모든 엔티티는 KG_NODE, 모든 관계는 KG_EDGE에 통합. 새 관계는 EDGE_TYPE만 추가하면 되고, 재귀 탐색(BOM 트리, 공급망 추적)이 단일 테이블 CTE로 가능.

KG_NODE 테이블 구조

모든 원본 테이블의 데이터가 하나의 KG_NODE 테이블에 로드됩니다. 각 행은 하나의 엔티티를 나타내며, 타입 접두사가 붙은 ID, 표시명, 그리고 원본 컬럼 전체를 VARIANT 타입의 PROPS 컬럼에 JSON으로 저장합니다.
CREATE TABLE KG_NODE ( NODE_ID STRING -- 'SUP_1', 'CMP_201', 'PRD_1001' NODE_TYPE STRING -- 'Supplier', 'Component', 'Product', ... NAME STRING -- 'Samsung SDI', 'Battery Cell 4680' PROPS VARIANT -- All original columns as JSON ) CLUSTER BY (NODE_TYPE);

Concrete Views (V_*) — 왜 필요한가?

KG 테이블만으로는 불편한 이유

KG_NODE/KG_EDGE는 모든 데이터를 VARIANT(JSON) 컬럼 PROPS에 저장합니다. 유연하지만, 매번 PROPS:PRICE::FLOAT처럼 JSON 경로를 파싱해야 합니다. Concrete View는 이 JSON 추출을 미리 수행하여 일반 컬럼처럼 사용할 수 있게 합니다.

Before — KG_NODE 직접 쿼리
SELECT PROPS:PRICE::FLOAT AS PRICE,
PROPS:CATEGORY::STRING AS CATEGORY
FROM KG_NODE
WHERE NODE_TYPE = 'Product'
After — V_PRODUCT 뷰 사용
SELECT PRICE, CATEGORY
FROM V_PRODUCT
JSON 파싱 불필요, 타입 안전, 자동완성 지원
각 엔티티/관계 타입마다 PROPS에서 특정 컬럼을 추출하는 타입별 뷰가 생성됩니다. JSON 파싱 없이 익숙한 SQL로 조회할 수 있습니다.

Layer 2는 왜 필요한가?

Layer 1의 KG_NODE/KG_EDGE는 데이터만 저장합니다. 하지만 "Supplier는 Organization의 하위 타입이다", "assembles_from은 재귀 탐색이 가능한 transitive 관계다"와 같은 데이터에 대한 지식(Knowledge)은 별도로 관리해야 합니다. 이것이 메타데이터 레이어의 역할입니다.

메타데이터가 있으면 아래 세 가지가 가능합니다:

(1) 새 클래스/관계 추가 — INSERT 한 줄로 해결

예: 새로운 엔티티 유형 LogisticsProvider(물류 업체)가 추가되는 상황. 코드 변경 없이 메타데이터 INSERT만으로 온톨로지가 확장됩니다.

Before — 메타데이터 없이
-- 1. 새 테이블 DDL 작성
CREATE TABLE LOGISTICS_PROVIDERS (...);
-- 2. KG_NODE INSERT 쿼리 수정
-- 3. 새 V_ 뷰 CREATE VIEW 작성
-- 4. VW_ONT_ORGANIZATION 뷰 수정 (UNION ALL 추가)
-- 5. VW_ONT_ALL_ENTITIES 뷰 수정
-- → 최소 5개 SQL 수작업 필요
After — 메타데이터 사용
-- 1. 클래스 등록 (INSERT 1줄)
INSERT INTO ONT_CLASS VALUES
  ('LogisticsProvider', 'Organization',
   FALSE, '물류 업체');

-- 2. 매핑 등록 (INSERT 1줄)
INSERT INTO ONT_CLASS_MAP VALUES
  (... 'LogisticsProvider', 'KG_NODE' ...);

-- 3. SP 한 번 호출 → 뷰 자동 재생성
CALL SP_GENERATE_ONTOLOGY_VIEWS();

(2) 추론 규칙 — 역방향 관계 자동 생성

예: supplies 관계만 입력하면, 추론 엔진이 supplied_by(역방향)를 자동으로 생성합니다.

Before — 역방향 수동 관리
-- supplies 엣지: SUP_1 → CMP_201
-- supplied_by 엣지도 직접 INSERT해야 함:
INSERT INTO KG_EDGE VALUES
  (UUID, 'CMP_201', 'SUP_1', 'supplied_by', ...);
-- 118개 supplies 엣지마다 수동 생성
-- 데이터 변경 시 동기화 문제 발생
After — 추론 규칙 사용
-- ONT_RULE에 규칙이 이미 등록됨:
-- RULE_INV_002: supplies → supplied_by

-- SP 한 번 호출하면:
CALL SP_INFER_INVERSE('RULE_INV_002');

-- 결과: 118개 supplied_by 엣지가
-- REL_EDGE_INFERRED에 자동 생성
-- 원본 데이터 변경 시 다시 호출만 하면 됨

(3) 뷰 자동 재생성 — SP 한 번 호출

예: 위에서 LogisticsProvider를 추가한 후, SP_GENERATE_ONTOLOGY_VIEWS()를 호출하면 ONT_CLASS_MAP을 읽어 VW_ONT_LOGISTICSPROVIDER 뷰를 자동 생성하고, VW_ONT_ALL_ENTITIES도 자동 갱신합니다.

-- SP가 ONT_CLASS_MAP 테이블을 순회하며 자동으로 뷰를 생성합니다: CALL SP_GENERATE_ONTOLOGY_VIEWS(); -- 결과: -- ✓ VW_ONT_LOGISTICSPROVIDER 뷰 생성됨 (새로 추가된 클래스) -- ✓ VW_ONT_ALL_ENTITIES 뷰 갱신됨 (새 클래스 UNION 포함) -- ✓ 기존 10개 VW_ONT_* 뷰도 함께 재생성됨 -- 반환값 예시: -- {"views_created": ["VW_ONT_SUPPLIER", ..., "VW_ONT_LOGISTICSPROVIDER", "VW_ONT_ALL_ENTITIES"], "count": 12}

Layer 3은 왜 필요한가?

기존 관계형 DB에서는 "모든 물리적 자산의 총 가치"를 구하려면 Component 테이블과 Product 테이블을 개별적으로 쿼리한 후 수동으로 합산해야 합니다. 새로운 자산 유형(예: Equipment)이 추가되면 쿼리도 수정해야 합니다.

Abstract View는 클래스 계층에 따라 자동으로 UNION합니다. PhysicalAsset 아래 새 클래스를 추가하면 뷰가 자동 갱신되므로 쿼리 변경이 불필요합니다.

Before — 개별 조회
SELECT 'Component', COUNT(*) FROM V_COMPONENT
UNION ALL

Layer 4는 왜 필요한가?

Layer 1~3은 데이터를 저장하고 구조화하지만, 자연어 질문을 SQL로 변환하려면 AI가 "REGION은 지역을 의미하고, total_orders는 COUNT(DISTINCT ORDER_ID)로 계산한다"는 것을 알아야 합니다. Semantic View는 이런 비즈니스 의미(시맨틱)를 Facts, Dimensions, Metrics, Synonyms으로 정의하여 Cortex Analyst가 정확한 SQL을 생성할 수 있게 합니다.

Layer 5는 왜 필요한가?

Semantic View 2개(Base + KG)와 Graph Traversal UDF 3개가 있으므로, 사용자가 질문할 때 어떤 Tool을 사용해야 하는지 판단해야 합니다. "Samsung SDI가 공급하는 부품은?"은 Base에, "Battery Cell 4680의 전체 BOM 트리"는 Graph UDF에 물어야 합니다.

Cortex Agent는 질문의 의도를 파악하여 자동으로 적절한 Tool을 선택하고 SQL을 생성/실행하여 결과를 반환합니다.

Stored Procedures & UDFs

추론 엔진과 그래프 도구는 왜 필요한가?

온톨로지의 진정한 가치는 명시적으로 입력하지 않은 관계를 자동으로 도출하는 데 있습니다. 예를 들어 "A가 B를 공급한다"만 입력하면 "B는 A로부터 공급받는다"(inverse)를 자동 생성하고, BOM의 재귀 관계를 따라 "원자재에서 최종 제품까지의 전체 경로"(transitive closure)를 계산합니다.
